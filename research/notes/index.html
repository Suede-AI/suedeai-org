Research notes

Working questions about consent records, changing creative files and the evidence needed to describe how AI tools were used.

By Jason Colapietro (Johnny Suede) · Founder & CEO of Suede AI

A consent record needs an object and an action

‘Permission granted’ is difficult to interpret without knowing what was presented and what use was requested. A useful record identifies the work, the person or organization involved, the proposed action, the response and the version of the terms shown. The research question is how to preserve that context so a later reviewer can understand the decision without reconstructing an entire conversation.

Changed files create a versioning question

A contributor may approve one mix while a later export contains a new vocal, edit or sample. A record tied only to a project title can hide that distinction. Preserve the approved file and identify the later version separately. A useful workflow should make it apparent when a prior approval belongs to a different version and when another decision is needed. The provenance page develops the file-history side of this problem.

Document model use as part of the process

For AI-assisted work, save enough information to explain the contribution: the tool used, the input materials, the outputs selected and the subsequent edits. Keep relevant permission records with the source materials. This gives collaborators a more useful account than a single label such as ‘AI-made’ or ‘human-made,’ which can hide a mixed process. It also helps the creator describe the work accurately when preparing a release.

A record and an enforcement mechanism are different

A record can preserve a stated preference or an agreement. Whether another system observes it depends on that system's behavior and the arrangement between the parties. Research should therefore test both the representation of the decision and the point where it is checked. Record what the receiving system actually does with the information instead of assuming that publishing a preference causes every downstream user to follow it.

Make an open question testable

Turn a broad question into an experiment with a named input and expected result. For example: can a recipient distinguish an approved export from a changed file using only the delivery packet? Give them both versions and the supporting records, then observe where the explanation fails. Document the conditions and result before changing the design. This produces evidence a collaborator can evaluate and a concrete question for the next iteration.
